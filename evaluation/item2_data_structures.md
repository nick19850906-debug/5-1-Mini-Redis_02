## 문항 2-1. 이중 연결 리스트의 노드 구조(`prev`, `next`, `data`)와 핵심 메서드들이 `O(1)`로 동작하도록 어떻게 구성했는지 설명할 수 있는가?

### 1) 질문 의도 해석
- 단순 배열(파이썬 `list`)과 달리 왜 노드마다 앞(`prev`)·뒤(`next`) 양방향 포인터를 두었는지, 그리고 왜 `DoublyLinkedList`가 `head`와 `tail`을 유지하고 노드 객체를 반환하는지가 `O(1)` 달성과 어떤 관계인지 설명하는 항목입니다.

### 2) 실생활 비유
- **양손을 잡은 줄서기**: 각 사람(`Node`)이 왼손으로 앞사람(`prev`), 오른손으로 뒷사람(`next`)을 잡고 있고 본인 짐(`data`)을 들고 있습니다. 줄 중간의 철수가 빠지거나 맨 앞으로 이동할 때, 줄 전체를 처음부터 찾을 필요 없이 **철수의 앞사람과 뒷사람이 서로의 손만 다시 잡으면(포인터 2~4개 변경)** 끝납니다.

### 3) 우리 코드 구현 및 시간 복잡도 분석 (`mini_redis/doubly_linked_list.py`)
```python
class Node:
    def __init__(self, data):
        self.prev = None   # 이전 노드 참조
        self.next = None   # 다음 노드 참조
        self.data = data   # 저장할 데이터 (LRU에서는 key 문자열)
```
- **핵심 메서드의 `O(1)` 설계 원리**:
  1. **`insert_front(data)` / `insert_back(data)`**: `self.head` / `self.tail` 끝점 포인터를 직접 들고 있으므로 순회 없이 새 노드를 바로 붙이고, **생성된 `Node` 객체 자체를 반환**합니다. (`Entry`가 이 노드 참조를 보관해야 이후 탐색 없이 `O(1)` 제거·이동 가능)
  2. **`remove_node(node)`**: `node.prev`와 `node.next`가 이미 노드 안에 저장되어 있으므로,
     - `node.prev.next = node.next` (앞 노드가 내 뒤를 가리키게)
     - `node.next.prev = node.prev` (뒤 노드가 내 앞을 가리키게)
     - 만약 `node`가 `head` 또는 `tail`이었다면 리스트의 `head`/`tail` 포인터만 갱신하면 **데이터 개수 $N$과 무관하게 상수 시간 `O(1)`** 으로 삭제됩니다. (단일 연결 리스트였다면 `prev`를 찾기 위해 `head`부터 $O(n)$ 순회가 필요했습니다.)
  3. **`move_to_front(node)`**: 이미 `head`면 즉시 반환하고, 아니면 `remove_node(node)`로 현재 위치에서 `O(1)` 분리한 뒤 `_link_front(node)`로 `head` 앞에 `O(1)` 연결합니다.
  4. **`remove_front()` / `remove_back()` / `__len__()`**: 각각 `head`, `tail`, `_size` 필드를 즉시 참조하므로 모두 **`O(1)`** 입니다.

### 4) 평가 모범 답변 (요약)
> "`Node`는 `prev`, `next`, `data` 3개 필드를 가지며, `DoublyLinkedList`는 `head`, `tail`, `_size`를 유지합니다. `insert_front`가 노드 참조를 반환하고 `Entry`가 이를 기억하기 때문에, 삭제(`remove_node`)나 최신화(`move_to_front`) 시 리스트를 순회하지 않고 양옆 노드의 `prev`/`next` 포인터 2~4개만 즉시 바꿔 모든 핵심 메서드가 `O(1)`로 동작합니다."

## 문항 2-2. 해시맵에서 직접 설계한 해시 함수가 어떤 입력을 받아 어떤 과정을 거쳐 인덱스를 만드는지 설명할 수 있는가?

### 1) 질문 의도 해석
- 임의의 문자열 키(영문, 숫자, 특수문자, 한글 등)가 어떤 수학적·비트적 변환 과정을 거쳐 고정 크기 버킷 배열의 유효한 정수 인덱스(`0 <= idx < capacity`)가 되는지 단계별로 설명할 수 있는지 검증합니다.

### 2) 실생활 비유
- **우편함 호수 계산기**: 입주민 이름(문자열)의 한 글자 한 글자를 숫자 코드로 바꾼 뒤 정해진 곱셈·덧셈 공식으로 큰 일련번호(해시값)를 만들고, 마지막으로 아파트 우편함 칸 수(`capacity`)로 나눈 **나머지**를 그 사람의 우편함 번호로 삼습니다.

### 3) 우리 코드에서의 4단계 변환 과정 (`mini_redis/hashmap.py`)
```python
def hash_key(key):
    h = 5381
    for b in key.encode("utf-8"):
        h = (h * 33 + b) & 0xFFFFFFFF
    return h
```
1. **입력(Input)**: 문자열 키 `key` (예: `"user:1"`, `"이름"`).
2. **UTF-8 바이트 시퀀스 변환**: `key.encode("utf-8")`로 문자열을 `0~255` 범위의 정수 바이트 열로 바꿉니다. 덕분에 ASCII뿐 아니라 한글·이모지 키도 동일한 방식으로 처리합니다.
3. **djb2 누적 혼합**: 초기값 `5381`에서 시작해 각 바이트 `b`를 순서대로 `h = (h * 33 + b) & 0xFFFFFFFF`로 누적합니다.
   - `h * 33`은 `(h << 5) + h`와 같아 비트 단위 연산이 빠르고, 순서가 다른 문자열(`"ab"` vs `"ba"`)도 전혀 다른 숫자로 퍼집니다.
   - `& 0xFFFFFFFF` 비트 마스크로 32비트 부호 없는 정수 범위(`0 ~ 4,294,967,295`)로 제한해 파이썬 임의 정밀도 정수가 끝없이 커져 연산이 느려지는 것을 방지합니다.
4. **버킷 인덱스 매핑**: `_bucket_index(key)`에서 **`hash_key(key) % len(self._buckets)`** (나머지 연산)를 수행해 항상 `0`부터 `버킷 수 - 1` 사이의 배열 인덱스를 만듭니다.

### 4) 평가 모범 답변 (요약)
> "직접 구현한 `hash_key`는 문자열 키를 UTF-8 바이트열로 변환한 뒤 초기값 `5381`에서 매 바이트마다 `h = (h * 33 + b) & 0xFFFFFFFF`를 적용하는 **djb2 해시 알고리즘**으로 32비트 정수를 생성합니다. 이후 이 해시값을 현재 버킷 수로 나눈 나머지(`hash_value % len(self._buckets)`)를 계산해 실제 배열 인덱스를 얻습니다."

## 문항 2-3. 충돌 해결을 체이닝 방식으로 어떻게 구현했는지(버킷 내부 구조 선택 포함) 설명할 수 있는가?

### 1) 질문 의도 해석
- 서로 다른 키가 같은 버킷 인덱스로 떨어지는 **해시 충돌(Hash Collision)** 을 어떻게 처리하는지, 특히 개방 주소법(Open Addressing) 대신 **체이닝(Separate Chaining)** 을 택한 이유와 각 버킷 내부 자료구조로 무엇을 선택했는지(배열 vs 연결 리스트) 설명하는 항목입니다.

### 2) 실생활 비유
- **우편함 속 줄 세우기**: 우연히 `101호` 우편함에 철수와 영희의 편지가 모두 배정되면, 옆집 `102호`로 밀어 넣는 대신(개방 주소법) `101호` 우편함 안에 **이중 연결 리스트 줄**을 만들어 `[철수, 값]`과 `[영희, 값]`을 나란히 연결해 둡니다.

### 3) 우리 코드 구현 및 버킷 내부 구조 선택 이유 (`mini_redis/hashmap.py`)
- **구조**: `self._buckets = [DoublyLinkedList() for _ in range(cap)]`
- **저장 형태**: 각 버킷 안의 노드는 `[key, value]` 2칸 리스트를 `node.data`로 보관합니다.
- **동작 방식 (`_find`, `put`, `get`, `remove`)**:
  - 조회/삽입/삭제 모두 `_find(key)`로 해당 버킷의 `head`부터 순회하며 `node.data[0] == key`인지 비교합니다.
  - **`put`**: 같은 키가 이미 체인에 있으면 `node.data[1] = value`로 값만 교체하고, 없으면 `bucket.insert_back([key, value])`로 체인 끝에 추가합니다.
  - **`remove`**: 체인에서 노드를 찾으면 **`bucket.remove_node(node)`** 를 호출해 `O(1)`로 끊어 냅니다.
- **왜 버킷 내부 구조로 `DoublyLinkedList`를 선택했는가?**
  1. **삭제 비용 최소화**: 파이썬 `list`를 버킷으로 쓰면 중간 키를 `pop(i)`할 때 뒤 요소를 한 칸씩 앞으로 밀어야 해 $O(k)$가 들고, 슬롯에 `TOMBSTONE` 표시를 남겨야 하는 개방 주소법의 복잡성도 피할 수 있습니다.
  2. **코드 재사용**: 이미 `O(1)` 삭제가 검증된 `DoublyLinkedList` 모듈을 그대로 버킷 체인으로 재사용해 중복 구현을 없앴습니다.
  3. **로드 팩터 관리와의 시너지**: 로드 팩터 `0.75` 이하로 유지되므로 평균 체인 길이는 1 미만($\le 0.75$)이어서 체인 탐색도 평균 `O(1)`로 끝납니다.

### 4) 평가 모범 답변 (요약)
> "해시맵은 각 버킷 슬롯마다 `DoublyLinkedList`를 두는 체이닝 방식으로 충돌을 해결합니다. 충돌 시 같은 버킷 리스트의 뒤에 `[key, value]` 노드를 연결하고, 조회 시 체인 내에서 `key`를 비교합니다. 버킷 내부에 파이썬 리스트 대신 직접 만든 이중 연결 리스트를 선택함으로써 삭제 시 배열 시프트 없이 `remove_node(node)`로 `O(1)` 제거가 가능하고, 개방 주소법의 클러스터링·삭제 마커(tombstone) 문제도 원천적으로 피했습니다."

## 문항 2-4. 로드 팩터 `0.75` 초과 시 "버킷 2배 확장"을 어떤 절차로 수행하는지 설명할 수 있는가?

### 1) 질문 의도 해석
- 해시맵에 데이터가 계속 늘어날 때 왜 크기를 늘려야 하는지, 임계치 `0.75`의 의미, 그리고 단순히 빈 버킷을 뒤에 덧붙이는 것이 아니라 **모든 기존 키를 다시 해싱(Rehashing)** 해야 하는 수학적 이유를 정확히 이해했는지 평가합니다.

### 2) 실생활 비유
- **아파트 동 증축 및 호수 재배정**: 8개 우편함에 편지가 7통(비율 0.875 > 0.75) 쌓이면 너무 붐비므로 우편함을 **16개로 2배 증축**합니다. 이때 우편함 번호 규칙이 `% 8`에서 `% 16`으로 바뀌었으므로, 기존 7통의 편지도 전부 꺼내 `% 16` 규칙으로 새 우편함에 다시 꽂아야(Rehash) 나중에 제대로 찾을 수 있습니다.

### 3) 우리 코드의 4단계 확장 절차 (`mini_redis/hashmap.py`)
1. **트리거 검사 (`put` 직후)**: 새 키를 넣어 `self._size += 1`이 된 뒤, 현재 로드 팩터 `self._size / len(self._buckets)`가 `LOAD_FACTOR_LIMIT(0.75)`를 초과하면 `_resize()`를 호출합니다.
   - 예: 초기 용량 `8`일 때 6개까지는 `6 / 8 = 0.75`로 유지, 7번째 키 삽입 시 `7 / 8 = 0.875 > 0.75`가 되어 확장 발동.
2. **기존 버킷 백업 및 2배 배열 생성**:
   - `old_buckets = self._buckets`로 기존 버킷 배열을 보관합니다.
   - `new_capacity = len(old_buckets) * 2` 크기의 새 버킷 배열(`[DoublyLinkedList() for _ in range(new_capacity)]`)을 할당합니다.
3. **전체 항목 재해싱(Rehash)**:
   - `old_buckets`의 모든 버킷과 체인 노드를 순회하며 기존 `(k, v)` 쌍을 꺼냅니다.
   - **`new_idx = hash_key(k) % new_capacity`** 로 새 인덱스를 다시 계산해 새 버킷에 삽입합니다.
   - *(주의: 기존 버킷 번호 그대로 복사하면 `hash_key(k) % (2*cap)` 결과와 불일치하여 `get(k)`가 키를 못 찾게 됩니다.)*
4. **분할 상환 시간 복잡도(Amortized `O(1)`)**:
   - `_resize()` 1회는 전체 $N$개 항목을 옮기므로 $O(N)$이 들지만, 버킷이 2배씩 커지므로 확장 주기도 2배씩 멀어집니다. 따라서 $N$번 삽입 동안 총 재해싱 비용은 $N + N/2 + N/4 + \dots < 2N$이 되어 삽입 1회당 **분할 상환 `O(1)`** 성능을 유지합니다.

### 4) 평가 모범 답변 (요약)
> "`put()`에서 새 키를 넣은 후 `size / bucket_count > 0.75`가 되면 `_resize()`를 호출합니다. 기존 버킷 배열을 임시 보관하고 크기가 2배인 새 버킷 배열을 만든 뒤, 기존 모든 `(key, value)` 쌍의 해시 인덱스를 `hash_key(key) % new_capacity`로 다시 계산해 재삽입(Rehash)합니다. 버킷이 2배씩 늘어나기 때문에 재해싱 비용은 분할 상환 `O(1)`이 되며 평균 체인 길이를 1 미만으로 유지해 조회 속도 `O(1)`을 보장합니다."
