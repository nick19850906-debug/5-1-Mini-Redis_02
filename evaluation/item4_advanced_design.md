# 항목 4 평가 분석: 확장성·정책 변경·메모리 모델 심화 설계 (3문항)

> 이 영역은 현재 구현된 아키텍처의 한계와 트레이드오프를 객관적으로 분석하고, 실제 프로덕션 Redis 수준으로 확장할 때 필요한 자료구조 변경과 평가 보정 전략을 제시하는 심화 문항입니다.

---

## 문항 4-1. "만약 LRU 대신 LFU 정책을 구현한다면 자료구조를 어떻게 변경해야 하는가?"에 합리적으로 답변할 수 있는가?

### 1) 질문 의도 해석
- **LRU(최근 사용 시간 기준)** 와 **LFU(사용 빈도수 기준)** 의 본질적 차이를 이해하고, "가장 적은 빈도(`min_freq`)를 가진 키 중 가장 오래된 키"를 여전히 **`O(1)`** 에 찾기 위해 어떤 자료구조 조합으로 바꾸어야 하는지 설계 능력을 평가합니다.

### 2) 실생활 비유
- **LRU(단일 줄)**: 방금 본 책 한 권을 무조건 책상 맨 위로 올리는 1줄 쌓기.
- **LFU(빈도별 책꽂이)**: "1번 읽은 책 칸", "2번 읽은 책 칸", "5번 읽은 책 칸"처럼 **횟수별로 여러 줄의 서가**를 두고, 책을 한 번 더 읽을 때마다 다음 횟수 칸의 맨 앞으로 옮깁니다. 책을 치울 때는 **가장 숫자가 작은 칸(`min_freq`)의 맨 아래 책(`tail`)** 을 꺼냅니다.

### 3) LFU를 `O(1)`로 구현하기 위한 자료구조 변경안
현재 `Entry + HashMap + 단일 DoublyLinkedList` 구조를 다음과 같이 확장합니다.

1. **`Entry` 확장 (`freq` 필드 추가)**:
   - 기존 `Entry(value, lru_node, expire_at)`에 접근 횟수 **`freq = 1`** 을 추가합니다.
2. **단일 리스트 → `freq_table` (빈도별 이중 연결 리스트 매핑) + `min_freq` 변수**:
   - `key_table`: 기존 `HashMap` (`key → Entry`)
   - `freq_table`: 두 번째 `HashMap` (`freq 정수 → 해당 빈도를 가진 키들의 DoublyLinkedList`)
   - `min_freq`: 현재 저장소에 존재하는 최소 접근 빈도수(정수)를 별도 추적합니다.
3. **핵심 연산의 `O(1)` 동작 방식**:
   - **조회/갱신 (`GET` / 기존 키 `SET`)**:
     1. `entry`의 현재 빈도 `f = entry.freq` 확인
     2. `freq_table.get(f)` 리스트에서 `entry.lru_node`를 `O(1)` 제거
     3. 만약 `f == min_freq`였고 그 빈도 리스트가 비어 버렸다면 `min_freq += 1`
     4. `entry.freq = f + 1`로 올리고 `freq_table.get(f + 1)` 리스트(없으면 새로 생성)의 `head`에 `insert_front` (`O(1)`)
   - **신규 삽입 (`SET`) & 방출 (`Eviction`)**:
     - 새 키는 항상 빈도 `1` 리스트의 `head`에 넣고 `min_freq = 1`로 리셋합니다.
     - 메모리 초과 시 `freq_table.get(min_freq).tail`을 `O(1)`로 제거합니다(동일 최소 빈도 내에서는 LRU 타이브레이커 역할 수행).
4. **보조 고려사항 (실무적 한계 보완)**:
   - 과거에 자주 쓰였으나 지금은 안 쓰는 키가 높은 `freq` 때문에 영원히 안 사라지는 문제(Cache Pollution)를 막으려면, 일정 주기마다 `freq`를 절반으로 줄이는 **Aging(LFU Decay, Redis 4.0+ Morris Counter)** 을 추가하는 것이 합리적입니다.

### 4) 평가 모범 답변 (요약)
> "LRU의 단일 `DoublyLinkedList`를 **`freq_table(빈도 → DoublyLinkedList)` 해시맵과 `min_freq` 정수 변수**로 대체하고, `Entry`에 `freq` 필드를 추가합니다. 키에 접근할 때마다 기존 `freq` 리스트에서 노드를 `O(1)`로 빼고 `freq + 1` 리스트의 `head`로 옮기며, 빈도가 가장 낮은 `min_freq` 리스트의 `tail`을 방출하면 LFU도 `O(1)`로 동작합니다. 여기에 오래된 인기 키 고착을 막기 위한 주기적 빈도 감쇠(Decay)를 더할 수 있습니다."

## 문항 4-2. "데이터가 10만 건으로 늘어나면 현재 구조에서 병목이 될 수 있는 부분은 어디이며, 어떻게 개선할 수 있는가?"에 답변할 수 있는가?

### 1) 질문 의도 해석
- 소규모(수십 건)에서는 드러나지 않지만 $N = 100,000$ 규모로 커졌을 때 **단일 스레드 Stop-the-World 정지(Latency Spike)** 나 **`O(n)` 선형 연산, 메모리 증폭**이 발생하는 병목 지점을 코드 수준에서 짚어내고 개선안을 제시할 수 있는지 평가합니다.

### 2) 현재 코드 기준 5가지 병목 지점과 개선안

| 번호 | 현재 코드의 병목 지점 | 10만 건일 때 발생하는 문제 | 합리적 개선 방안 |
| :---: | :--- | :--- | :--- |
| **1** | **`HashMap._resize()`의 일괄 재해싱** (`hashmap.py`) | 10만 건 부근(예: `65,536 * 0.75` 초과로 `131,072` 확장 시) 단 한 번의 `SET` 호출이 **10만 개 전체 노드를 재삽입하느라 수십~수백 ms 멈춤(Latency Spike)** 발생 | **점진적 재해싱(Incremental Rehashing)**: 실제 Redis처럼 `ht[0]`, `ht[1]` 두 테이블을 두고 매 명령마다 버킷 몇 개씩만 조금씩 옮겨 멈춤 시간 분산 |
| **2** | **매 명령 전 `purge_expired()` 무한 루프** (`ttl.py`) | 만약 10만 건의 키가 같은 시각에 일괄 만료되면 다음 단일 명령 한 번이 10만 번 `heap.pop()`(`O(n log n)`)을 다 돌 때까지 블로킹됨 | **최대 처리 한도(Budget) 설정 + 확률적 샘플링**: 한 번 호출 시 최대 `K`개(예: 20~50개) 또는 1ms 이내만 청소하고 나머지는 다음 틱/접근 시 Lazy하게 처리 |
| **3** | **최소 힙 Lazy Deletion의 낡은 엔트리 누적** (`ttl.py`) | `SET`/`EXPIRE` 덮어쓰기나 `DEL`이 10만 번 반복되면 해시맵 크기는 작아도 힙 배열에 죽은 튜플이 계속 쌓여 **힙 높이와 메모리가 비대**해짐 | **유효 항목 대비 힙 크기 비율 임계치**(예: `heap.size() > dbsize * 2`) 초과 시 유효한 키만 추려 `heapify` 재구축(`O(n)`), 또는 힙 인덱스 맵으로 즉시 삭제(`O(log n)`) |
| **4** | **`KEYS` 명령의 전체 순회** (`hashmap.py`) | 10만 개 버킷과 체인을 전부 훑어 한 번에 큰 리스트를 만들고 직렬화하므로 그동안 다른 명령이 완전히 차단됨 | **커서 기반 점진 조회(`SCAN cursor COUNT N`)** 도입으로 한 번에 소량씩 분할 반환 |
| **5** | **파이썬 객체 메모리 오버헤드 & `djb2` 파이썬 루프** | 10만 개의 `Entry` + `Node` + `[k, v]` + 튜플이 각각 수백 바이트씩 차지해 순수 문자열보다 수 배~수십 배 RAM 소모 | `__slots__` 선언으로 객체별 `__dict__` 제거, 버킷을 2칸 리스트 대신 `Entry` 직접 연결 또는 C/Cython/해시 캐싱 적용 |

### 3) 평가 모범 답변 (요약)
> "10만 건 규모에서는 ① `HashMap._resize()`가 일괄 재해싱으로 한 번에 수십 ms 멈추는 현상, ② 동시 대량 만료 시 `purge_expired()`가 한 명령 안에서 모두 처리하느라 블로킹되는 현상, ③ 덮어쓰기·삭제로 힙 안에 죽은 튜플이 누적되는 현상, ④ `KEYS` 전체 스캔과 ⑤ 파이썬 `Entry`/`Node` 객체 오버헤드가 주요 병목입니다. 이를 실제 Redis처럼 **점진적 재해싱(Incremental Rehash)**, **만료 청소 상한(Budget) 제한**, **힙 재구축 임계치**, **`SCAN` 커서 도입**, **`__slots__` 적용**으로 개선할 수 있습니다."

## 문항 4-3. "`used_memory`에 자료구조 오버헤드까지 포함하는 모델로 바꾸면 무엇이 달라지고, 공정한 비교/채점을 위해 어떤 보정이 필요할지" 설명할 수 있는가?

### 1) 질문 의도 해석
- 현재의 단순화 모델(`len(utf8(key)) + len(utf8(value))`)과 실제 메모리 할당 모델(`Entry`, `Node`, 버킷 배열, 힙 튜플 등 포함)의 차이를 인식하고, 서로 다른 언어·구현체 간에 오버헤드 모델을 적용했을 때 생기는 **채점 불공정성 문제를 어떻게 보정할지** 시스템 관점에서 사고할 수 있는지 평가합니다.

### 2) 오버헤드 포함 모델로 바꾸면 달라지는 점
1. **작은 키·값일수록 오버헤드 비중이 폭증**:
   - 현재 모델에서 `SET a 1`은 단 `2바이트`입니다.
   - 하지만 64비트 CPython 기준으로는 문자열 객체 헤더(~49B) + `Node` 인스턴스(인스턴스 `__dict__` 포함 약 150~200B) + `Entry` 인스턴스(~150B) + 해시맵 체인 `Node` + `[k, v]` 리스트 + 힙 튜플까지 합쳐 **실제 RAM은 건당 수백 바이트(예: 400~600B)** 에 달합니다.
2. **동작 변화 3가지**:
   - **작은 `maxmemory` 설정 시 즉시 OOM 발생**: `CONFIG SET maxmemory 30` 같은 테스트는 오버헤드 1건만으로도 30B를 넘겨 아무것도 저장할 수 없게 됩니다.
   - **방출(Eviction) 시점 변화**: 빈 버킷을 늘리는 `_resize()` 순간에도 `used_memory`가 급증해, **데이터 삽입이 아닌 리사이즈나 `EXPIRE`(힙 push)만으로도 `maxmemory`를 초과해 Eviction이 연쇄 발생**할 수 있습니다.
   - **`DEL` 후에도 회수 지연**: Lazy Deletion 때문에 힙에 남아 있는 죽은 튜플의 메모리가 즉시 회수되지 않아 `used_memory`가 실제 데이터 수와 어긋납니다.

### 3) 공정한 비교·채점을 위해 필요한 보정 방안
언어(Python vs C/Go/Java)와 구현 방식(인스턴스 객체 vs `__slots__` vs 인라인 배열)에 따라 `sys.getsizeof()` 수치가 크게 달라지므로 그대로 절대 바이트로 채점하면 공정성이 무너집니다. 이를 위해 다음 **4가지 보정 규칙**이 필요합니다.

1. **표준화된 추상 비용 테이블(Abstract Cost Model) 고정**:
   - 런타임의 `sys.getsizeof()` 대신 채점 명세에서 고정 가중치(예: `Node = 24B`, `Entry = 32B`, `Bucket Slot = 8B`, `Heap Item = 16B`, `+ UTF-8(key) + UTF-8(value)`)를 명시해 모든 구현체가 동일한 계산식으로 산정하도록 표준화합니다.
2. **가변 간접 비용(버킷 확장 / Lazy Heap 잔여물) 분리 또는 상한 지정**:
   - 버킷 재할당으로 인한 일시적 슬롯 증가분이나 힙의 지연 삭제 잔여 튜플을 `used_memory`에 포함할지, 아니면 `overhead_memory`로 분리해 `INFO memory`에서 별도 리포트할지 명세를 확정합니다.
3. **테스트 한도(`maxmemory`) 스케일링 및 허용 오차 범위 채점**:
   - 고정 오버헤드 `O_per_entry`가 크므로 테스트의 `maxmemory` 기준값을 `k * (데이터 크기 + 고정 오버헤드)` 형태로 상향 스케일링하고, 1건 차이로 합불이 갈리지 않도록 **상대 오차 범위(예: ±5% 또는 최종 생존 키 집합의 순서·개수 일치 여부)** 로 판정합니다.
4. **알고리즘 효율성 중심 채점 유지**:
   - 언어 자체의 객체 크기 차이로 불이익을 주지 않으려면, 물리 RAM 총량 비교보다 **동일 조건에서의 방출 순서(LRU 정합성), `evicted_keys` 단조 증가, 메모리 누수 없음(`DEL` 전후 `used_memory` 복원)** 을 핵심 합격 기준으로 삼는 것이 공정합니다.

### 4) 평가 모범 답변 (요약)
> "오버헤드를 포함하면 `Entry`, `Node`, 해시 버킷, 힙 튜플 비용 때문에 작은 키도 수백 바이트를 차지하고, `_resize()`나 `EXPIRE` 호출만으로도 메모리가 늘어나 Eviction 시점이 앞당겨집니다. 또한 파이썬과 C/Go 간 객체 크기 차이가 크므로 공정한 비교·채점을 위해서는 ① `sys.getsizeof()` 대신 명세서상 고정 추상 바이트 모델(`Node=X`, `Entry=Y`)을 합의하거나, ② 테스트 `maxmemory`를 오버헤드에 비례해 스케일링하고, ③ 절대 바이트 일치 대신 `DEL` 후 메모리 완벽 복원 여부와 방출 순서(LRU 정합성) 중심으로 채점 기준을 보정해야 합니다."
